# 9月1日本次需求汇总

> 本文档只记录本次新增需求。此前需求已经完成，不在本文档范围内，也不作为本次开发的实施内容。

## 1. 使用日志自动刷新

### 1.1 已确认需求

1. 在使用日志页面“紧凑列表”按钮左侧增加一个 `Switch`。
2. 开启后，使用日志列表和顶部统计每 3 秒自动刷新。
3. 支持随时启用和禁用；禁用后立即停止后续轮询。
4. 离开使用日志页面、切换路由或组件卸载时，必须清理定时器和未完成请求，不能继续访问日志接口。
5. 自动刷新必须保留当前筛选条件、分页、排序、列设置和列表展示模式，不能重置用户当前视图。
6. 上一轮刷新未完成时不得发起下一轮相同请求，避免并发轮询。
7. 刷新失败时保留已有数据并提示失败原因，不能因为一次失败清空列表或阻塞下一轮刷新。
8. 自动刷新开关、刷新中、刷新失败和状态提示需要补齐现有多语言。

### 1.2 验收标准

1. 开启开关后可以稳定按 3 秒间隔刷新列表和统计数据。
2. 关闭开关后不再产生新的轮询请求。
3. 切换筛选、分页或排序后，下一轮刷新使用最新参数。
4. 离开页面后不再产生轮询请求，也不出现卸载组件更新状态的警告。
5. 模拟接口慢响应和接口失败时，不会产生并发请求、空白页面或数据闪烁。

## 2. 渠道探测写入使用日志

### 2.1 背景

渠道探测请求会访问上游并可能产生真实 Token 消耗，但目前主要记录在监控检查或系统事件中，未完整进入使用日志，导致本站记录无法与上游账单逐条对账。

### 2.2 已确认需求

1. 渠道探测请求必须写入使用日志。
2. 探测日志必须与普通用户请求明确区分，不能伪装成普通用户、普通令牌或普通消费请求。
3. 日志至少记录：
   - 渠道、渠道 ID。
   - 探测分组、分组 ID和探测任务 ID（有值时）。
   - 探测模型和实际请求模型。
   - 请求时间和请求标识。
   - 请求状态、错误分类、HTTP 状态码、上游错误码和错误信息。
   - 总响应耗时和 TTFT（可取得时）。
   - 输入、输出、缓存和总 Token。
   - 费用或标准口径消耗。
4. 探测成功且上游返回 usage 时，必须记录上游真实 usage 和标准口径消耗。
5. 探测失败时，已经取得的部分 usage 必须保留，不能无条件覆盖为 `0 / 0`。
6. 探测日志必须带结构化来源标识，例如 `monitor_probe`，便于日志列表筛选和展示。
7. 探测日志不能扣除普通用户额度、增加普通用户调用次数或污染普通用户排行榜。
8. 管理员能够筛选和识别探测日志；普通用户不能看到管理员渠道探测及认证信息。
9. 同一次探测只能产生一条最终使用日志。发生重试时需要保留尝试链路和最终结果关联，不能重复计费或重复写入最终记录。

### 2.3 统计与结算边界

- 探测费用必须采用标准口径，不能套用用户分组倍率或用户侧优惠。
- 需要区分“未取得 usage”“取得部分 usage”和“取得最终 usage”三种状态。
- 探测请求的标准口径消耗可以用于渠道对账，但不能进入普通用户消费统计。
- 优先复用现有 `logs` 表、使用日志接口和消耗详情结构，不重复建设一套日志表。

### 2.4 验收标准

1. 成功探测后，使用日志能检索到唯一对应记录。
2. 失败探测后，日志能显示渠道、模型、错误分类、状态码或上游错误码和错误信息。
3. 日志中的 Token、耗时和标准口径消耗与探测实际结果一致。
4. 探测日志能通过请求标识、渠道 ID、分组 ID或任务 ID关联监控检查记录。
5. 探测不会改变普通用户额度、调用次数和排行统计。
6. 重试、异步落库和服务重启不会导致重复日志或重复扣费。

## 3. 用户列表排序

### 3.1 已确认需求

1. 用户列表为“剩余额度”增加排序。
2. 用户列表为“邀请人数”增加排序。
3. 两个表头点击都使用三态切换：升序 → 降序 → 不排序。
4. “不排序”状态恢复系统默认排序，不得残留上一次的排序字段或方向。
5. 排序必须由后端在完整结果集上执行，不能只对当前分页数据排序。
6. 排序需要与搜索、用户组筛选、状态筛选、分页和列设置兼容。
7. 空值、相同值和负额度需要稳定排序；相同值使用用户 ID或创建时间作为确定性兜底排序。
8. 排序字段、方向、三态状态和错误提示需要补齐多语言。

### 3.2 验收标准

1. 点击“剩余额度”可以依次切换升序、降序和不排序。
2. 点击“邀请人数”可以依次切换升序、降序和不排序。
3. 翻页、搜索和筛选后，排序字段和方向仍然正确。
4. 排序结果来自完整查询结果，不能出现仅当前页排序的情况。
5. 相同值多次查询顺序稳定，不能出现无原因跳动。
6. 普通用户不能通过排序参数访问管理员用户列表。

## 4. 渠道额度字段统计口径说明

### 4.1 已确认需求

1. 在渠道列表“今日/10日”旁增加信息图标。
2. 在渠道列表“已用/限额”旁增加信息图标。
3. 鼠标悬停信息图标时显示说明：统计按标准口径累计，不受分组倍率和用户侧优惠影响。
4. 如需区分两列的含义，可以在同一个 Tooltip 中分别说明“用量统计口径”和“限额统计口径”。
5. Tooltip 不能遮挡关键表格内容，紧凑列表、自适应列表和窄屏布局都要能完整查看。
6. 信息图标、Tooltip 文案和无障碍标签需要支持现有多语言。
7. 本需求只增加解释性 UI，不改变渠道用量、限额结算、无限额显示或多密钥汇总逻辑。

### 4.2 验收标准

1. 桌面端鼠标移入图标可以看到完整的统计口径说明。
2. 键盘聚焦和触摸设备有等价方式查看说明。
3. 不同列表展示模式下 Tooltip 不被裁剪或遮挡。
4. 所有现有额度数值、单位和计算结果保持不变。

## 5. 运营监控明细筛选

### 5.1 已确认需求

运营监控中的每个指标入口必须打开已经应用对应条件的请求明细，不能全部打开同一份未过滤列表。

| 指标入口 | 明细筛选条件 |
|---|---|
| 所有请求 | 当前时间窗口内的全部请求 |
| SLA 请求 | 当前时间窗口内属于 SLA 范围的请求 |
| 错误请求 | 当前时间窗口内失败的请求 |
| 请求时长 | 满足请求时长指标条件的请求 |
| TTFT | 满足首 Token 时间指标条件的请求 |
| 上游错误请求 | 仅上游失败的请求 |

明细需要继承运营监控当前时间范围，以及入口携带的模型、分组或其他上下文；页面或模态框中需要明确展示当前已应用的筛选条件。

### 5.2 错误明细字段

错误请求明细至少展示：

- 错误分类。
- HTTP 状态码和上游错误码（有值时分别展示）。
- 错误信息和经过权限控制的上游响应摘要。
- 渠道、模型、分组和请求标识。
- 请求时间、总响应耗时和 TTFT。
- 输入、输出、缓存和总 Token。
- 是否流式、是否客户端中断、是否完成结算。

### 5.3 实施与验收标准

1. 前端入口传递明确的指标类型或结构化筛选参数，不能只传一个展示文本。
2. 后端校验并转换筛选参数为真实查询条件，不能完全依赖前端过滤。
3. 各入口返回的每条明细都必须满足对应条件；无匹配数据时显示该条件下的空状态，不能回退到全量列表。
4. 明细支持分页、排序和刷新，关闭详情后恢复运营监控页面原有状态。
5. 错误明细覆盖上游错误、HTTP 错误、解析错误、超时、客户端中断和未完成 usage 等分类。

## 6. 告警和系统日志详情

### 6.1 已确认需求

1. “最新告警”中的错误请求支持点击查看具体错误详情。
2. “系统运行日志”条目支持点击查看对应日志详情。
3. 打开明细页或详情面板时，必须携带正确的请求 ID、事件 ID或结构化筛选条件，不能只显示摘要或跳转全量列表。
4. 从最新告警进入时，详情聚焦对应错误请求；从系统运行日志进入时，详情聚焦对应系统事件及其关联请求、渠道探测或后台任务。
5. 一个系统事件关联多条请求时，展示关联关系并支持继续查看对应请求；没有关联请求时，独立展示事件级详情。
6. 详情至少包含时间、级别、来源组件、错误分类、错误码、错误信息、请求 ID或事件 ID、渠道、模型、耗时、TTFT、Token usage和结算状态等已有数据。
7. 详情必须遵循管理员权限和敏感信息脱敏规则，不能泄露完整渠道密钥、用户密钥或上游认证信息。
8. 关闭详情后，原页面恢复滚动位置、筛选、分页和展示状态。
9. 入口、加载状态、空状态、错误状态和返回操作需要补齐多语言。

### 6.2 验收标准

1. 点击任意最新错误告警，打开的详情与该告警对应的请求一致。
2. 点击任意系统运行日志，打开的详情与该事件一致，不展示其他事件或全量请求。
3. 从不同入口进入同一请求时，详情内容和请求标识一致。
4. 无关联请求的系统事件仍可独立查看完整事件信息。
5. 详情加载失败、记录已删除或权限不足时有明确提示，且不会导致运营监控页面渲染失败。

## 7. 本次实施边界

1. 本文档只包含本次六项需求，不重复记录此前已完成的需求。
2. 实施范围限定在本地开发分支，暂不修改生产环境。
3. 代码实施前需要分别确认现有接口、数据结构和页面组件，避免重复建设已有能力。
4. 每项需求完成后分别进行针对性测试，并在全部验收通过后再提交 Git 和部署线上。
