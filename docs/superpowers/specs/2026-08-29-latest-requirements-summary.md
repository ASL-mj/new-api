## 3. 多密钥渠道限额汇总展示

### 3.1 问题

渠道管理列表的“已用 / 限额”列当前直接读取渠道整体 `quota_limit`。当渠道使用多密钥独立限额、而渠道整体限额为 `0` 时，列表会显示“已用 / ∞”。

这与实际配置不符：每个密钥已有独立上限，管理员无法从列表快速看到该渠道的总限额。

### 3.2 已确认需求

1. 多密钥渠道启用密钥限额时，渠道列表的限额不能显示为无限。
2. 该列应展示所有已配置密钥限额的合计值。
3. 已用额度应展示对应密钥已用额度的合计值，保证分子与分母处于同一统计口径。
4. 没有任何密钥限额时，才继续显示 `∞`。
5. 单密钥渠道和仅使用渠道整体限额的渠道，保持现有渠道级展示规则不变。

### 3.3 展示规则

| 渠道限额模式 | “已用 / 限额”主展示 |
|---|---|
| `none` | 渠道当前已用 / `∞` |
| `channel` | 渠道整体本轮已用 / 渠道整体限额 |
| `key` | 所有密钥本轮已用合计 / 所有已配置密钥限额合计 |
| `both` | 渠道整体本轮已用 / 渠道整体限额；同时在 Tooltip 中展示“密钥限额合计：已用 / 限额” |

其中，密钥限额合计只统计配置了正数限额的密钥；若任一可用密钥没有限额，则密钥合计上限为 `∞`。这是因为该密钥仍可持续承接请求，不能将整个渠道误展示为有限总额度。

### 3.4 后续实施范围

后续实现应复用现有多密钥用量接口和 `ChannelUsageCells` 渲染器，不在渠道主表中存储冗余合计字段：

- 批量用量接口需要返回每个渠道的密钥额度、密钥已用额度及是否存在不限额密钥。
- 渠道列表根据 `quota_limit_mode` 选择渠道级或密钥汇总级的展示口径。
- 多密钥管理弹窗需要支持密钥名称编辑，并在编辑入口中继续配置该密钥额度和状态。
- 需要覆盖单密钥、全部密钥有限额、部分密钥不限额、`both` 模式和无用量数据的渲染测试。

### 3.5 验收标准

1. 多密钥独立限额渠道在列表中能看到密钥限额合计，不再错误显示为 `∞`。
2. 列表中的已用值与限额值都来自密钥汇总，单位与现有金额展示一致。
3. 存在不限额可用密钥时，列表准确显示 `∞`。
4. `both` 模式保留渠道整体限额作为主展示，并能查看密钥限额合计。
5. 不影响渠道调度、自动禁用、限额结算和多密钥管理功能。

### 3.6 多密钥名称与编辑入口

1. 多密钥管理中为每个密钥增加“密钥名称”字段。
2. 密钥名称用于管理员区分多个密钥，可以新增和编辑。
3. 密钥名称只作为密钥别名展示，不替代真实密钥，也不能泄露完整密钥内容。
4. 多密钥列表中应显示密钥名称；名称为空时沿用现有的密钥序号或脱敏摘要作为兜底展示。
5. 将当前多密钥管理中的“限额”操作按钮改为“编辑”按钮。
6. 点击“编辑”后打开密钥编辑弹窗，至少包含：
   - 密钥名称
   - 该密钥的限额开关
   - 限额单位
   - 限额数值
   - 当前已用额度和剩余额度
7. 编辑保存时支持只修改名称、只修改限额或同时修改名称和限额。
8. 保存密钥名称不能改变真实密钥内容、渠道归属、密钥顺序和当前启用状态。
9. 限额编辑必须继续遵守本节的金额单位、多密钥汇总和无限额展示规则。
10. 编辑弹窗中的保存、取消、校验、错误提示和成功提示需要复用现有弹窗及多语言体系。
11. 名称过长、名称为空、名称重复和特殊字符需要按照当前项目表单校验规范处理；不能因为名称展示导致表格溢出。

### 3.7 实施范围

- 优先扩展当前多密钥数据结构中的可选名称字段；如果没有合适的持久化位置，再增加兼容旧数据的数据库字段或配置字段。
- 多密钥查询接口需要返回脱敏后的密钥信息、名称、限额配置、用量和状态；不返回不必要的完整密钥内容。
- 新增或修改密钥编辑接口必须进行管理员权限校验，并保证名称和限额更新具有一致性。
- 渠道列表、多密钥管理弹窗和限额汇总展示必须使用同一份名称与限额数据。

### 3.8 验收标准

1. 多密钥列表中能看到每个密钥的名称或合理的兜底名称。
2. 管理员可以编辑并保存密钥名称，刷新页面后名称仍然存在。
3. 原“限额”按钮已替换为“编辑”按钮。
4. 编辑弹窗中可以配置名称和限额，保存后列表和渠道汇总同步更新。
5. 编辑名称不会修改真实密钥、渠道归属、顺序或启用状态。
6. 完整密钥不会因为名称编辑功能出现在列表、接口响应或日志中。
7. 空名称、长名称、重复名称、无权限和保存失败场景均有明确处理。

## 5. 使用日志消耗 Token 统计

### 5.1 已确认需求

1. 使用日志页面顶部的“消耗额度”旁边新增“消耗 Token”统计项。
2. “消耗 Token”统计当前页面筛选时间范围内的 Token 总消耗量。
3. 该统计项必须与当前“消耗额度”使用完全相同的筛选条件，包括日志类型、时间范围、用户、令牌、模型、渠道和分组。
4. 管理员查看全部日志和普通用户查看个人日志时，都需要正确显示该统计项。
5. 没有日志或没有 Token 数据时显示 `0`，不能显示空白或 `NaN`。

### 5.2 统计口径

消耗 Token 总量定义为筛选结果中每条日志的：

```text
PromptTokens + CompletionTokens
```

只统计当前日志统计接口实际纳入的记录，不能把分页表格当前页的 Token 相加，因为分页数据不代表完整筛选结果。

当前后端 `Stat.tpm` 实际上已经通过 `sum(prompt_tokens) + sum(completion_tokens)`计算区间总 Token，但前端将其标记为 `TPM`。后续实现应复用这份统计结果并统一命名，避免新增重复查询或让“消耗 Token”和现有 `TPM` 展示相同数据却产生不同口径。

### 5.3 后续实施范围

- 扩展现有日志统计响应或统一现有 `tpm` 字段的展示语义，保持管理员和用户统计接口一致。
- 在 `web/src/components/table/usage-logs/UsageLogsActions.jsx` 的顶部统计区域增加“消耗 Token”展示。
- 与“消耗额度”共享加载、骨架屏、筛选刷新和错误处理状态。
- 根据现有数字格式化规范显示大数值，并支持多语言文案。
- 保留现有 RPM/TPM 兼容行为；若将 `TPM` 改为更准确的速率指标，必须另行确认统计口径，不能在本需求中直接改变。

### 5.4 验收标准

1. 选择任意时间范围和筛选条件后，顶部“消耗 Token”与数据库中对应筛选结果的 `prompt_tokens + completion_tokens` 总和一致。
2. 修改日期、用户、令牌、模型、渠道或分组筛选后，额度和 Token 统计同步刷新。
3. 管理员和普通用户看到的统计范围符合各自权限边界。
4. 空数据、Token 为零和大数值场景显示正常。
5. 不影响日志列表分页、详情查看、额度统计和现有 RPM/TPM 展示。

## 7. 使用日志消耗详情增强

### 7.1 需求背景

参考 Pite 使用日志的真实消费详情界面，在使用日志详情模态框中高还原复刻一套从请求信息、Token 统计到最终扣费的完整消费解释。此次视觉改造只作用于“消耗详情”弹窗，不修改使用日志列表、顶部统计、筛选区、导航、其他弹窗或全局 UI。数据、权限、计费逻辑和多语言仍使用当前 NewAPI 实现。

当前视觉原型：`.superpowers/brainstorm/14787-1787944747/content/usage-log-detail-prototype-v5.html`。

### 7.2 详情模态框整体结构

详情弹窗按以下顺序组织内容：

1. 顶部标题区：显示日志类型标识（例如“消耗”）、日志编号或短 ID、标题“消耗详情”和关闭入口。
2. 请求概览区：采用 Pite 的紧凑两列网格，按以下顺序排列：`请求 ID / 分组`、`令牌 / 调用模型`、`推理强度 / 响应时间`。
3. 消耗明细区：展示请求路径、复制路径入口、原生格式入口，以及输入、输出和缓存 Token 统计。
4. 计费详情区：展示计费模式、命中阶梯、各项 Token 计费公式、分项合计、倍率和最终扣费。
5. 按日志类型和权限显示现有扩展信息，例如渠道、上游模型、流状态、错误原因、参数覆盖和渠道亲和性。

### 7.3 请求概览展示内容

请求概览区至少支持以下字段：

| 字段 | 展示要求 |
|---|---|
| Request ID | 完整显示或提供复制能力，过长时允许折行，不得截断后无法查看完整值 |
| 调用模型 | 显示本次请求使用的模型；与请求 ID、令牌、分组等信息同属请求概览，不得遗漏 |
| 令牌 | 显示令牌名称；管理员按权限显示，普通用户不泄露管理员专属信息 |
| 分组 | 显示本次请求实际使用的分组 |
| 模型 | 显示请求并计费模型；存在模型映射时同时显示实际模型 |
| 推理强度 | 有值时显示 `low`、`medium`、`high`、`xhigh` 等实际值 |
| 响应时间 | 显示总耗时，并在同一字段中显示首字时间，例如 `6.0s (FRT: 0.7s)`；无数据时按现有空值规则处理 |

### 7.4 消耗明细展示内容

消耗明细区需要包含：

1. 请求路径，例如 `POST /v1/responses`，提供一键复制路径的图标入口。
2. “原生格式”入口，用于查看当前日志保存的原始或原生格式详情；没有原生内容时不显示无效入口。
3. 输入 Token 数量。
4. 输出 Token 数量。
5. 缓存读取 Token 数量。
6. 缓存命中率，按真实输入和缓存读取数据计算；没有缓存数据时显示 `0%` 或按统一空值规则展示，不能伪造命中率。
7. 如果当前日志存在缓存写入、缓存创建或其他供应商特有 Token 字段，应在缓存区域中继续拆分显示，并保留总缓存 Token 的可理解汇总。

统计数字使用统一的千位分隔格式，字段名称和数值上下排列，保持列表中 Tokens 列的输入/输出/缓存语义一致。

### 7.5 计费详情展示内容

计费详情区采用“公式 + 结果”的逐项解释形式：

1. 标题栏显示当前计费模式，例如“价格模式”；存在阶梯计费时显示当前命中的价格阶梯，例如“标准”。
2. 每一项费用独立一行，至少支持：
   - 输入：`Token 数 × 输入单价 / 1M Token = 分项金额`
   - 输出：`Token 数 × 输出单价 / 1M Token = 分项金额`
   - 缓存读取：`Token 数 × 缓存单价 / 1M Token = 分项金额`
3. 对 Claude、音频、图片、任务、阶梯表达式和其他已有计费类型，沿用现有计费计算器和展示逻辑，不将所有类型强行套入文本模型公式。
4. 显示分项合计，明确展示分组倍率、专属倍率或其他实际生效倍率。
5. 最终扣费单独高亮，公式应能表达为：

```text
分项合计 × 生效倍率 = 最终扣费
```

6. 最终扣费必须与日志实际 `quota` 及当前货币展示设置一致，不能因详情展示格式转换产生新的计费结果。
7. 违规扣费、订阅抵扣、退款、预扣费、失败请求等特殊日志必须显示对应语义，并隐藏不适用的正常计费行。

### 7.6 UI 与交互要求

1. 消耗详情弹窗直接以 Pite 消费详情界面作为视觉目标，高还原复刻以下特征：米白/浅色内容底、深色细边框、紧凑内边距、清晰的横向分隔线、低圆角或近似直角的分区、等宽数字和公式排版、蓝色最终扣费区域。
2. 弹窗采用 Pite 风格的宽屏比例和分区布局，不使用厚重的圆角卡片堆叠；顶部标题区、请求概览区、消耗明细区、计费详情区之间保持明确但紧凑的层级。
3. 请求概览固定使用两列网格：第一行 `请求 ID / 分组`，第二行 `令牌 / 调用模型`，第三行 `推理强度 / 响应时间`。Request ID 过长时允许在单元格内换行，不能挤压或遮挡旁边字段。
4. 消耗明细区使用三列并排展示输入、输出、缓存读取；字段名称在上、数字在下，缓存读取比例紧跟字段名称显示。
5. 计费详情区使用 Pite 风格的逐行公式布局：左侧为费用项，中间为公式，右侧为分项金额；底部左侧显示“分项合计 × 生效倍率 = 结算金额”，右侧使用蓝色区域突出“最终扣费”。
6. 可以复用 NewAPI 的 Semi UI、主题变量、图标和多语言能力，但视觉结果以 Pite 的上述布局和样式为准；不得因为复用组件而退回原有 Descriptions 展开行样式。
7. 点击列表行、费用胶囊或详情摘要均打开同一个详情弹窗，并定位到对应日志，不能重复打开多个弹窗。
8. Request ID、请求路径和可复制的模型名称沿用现有复制工具和成功提示。
9. 原生格式、错误详情、参数覆盖和渠道亲和性等内容采用现有弹窗或折叠内容组件承载，避免详情弹窗无限纵向膨胀。
10. 移动端按单列排列概览字段和费用项，长 Request ID、路径、错误信息可以折行，不能产生横向滚动遮挡关键信息。
11. 所有新增字段支持现有中文、英文和其他语言包；翻译缺失时不能把内部字段名直接暴露给用户。

### 7.7 数据与实现边界

- 优先复用现有日志记录中的 `prompt_tokens`、`completion_tokens`、`quota`、`other`、模型价格和计费过程数据，不重复计算或重新扣费。
- 缓存命中率、分项金额和倍率展示必须使用与后端结算相同的口径；前端只负责格式化和解释，不改变计费结果。
- 没有某个字段时按日志类型条件渲染，不渲染空标题、空分区或无效复制按钮。
- 管理员专属的渠道、用户、上游和审计信息继续遵守现有权限边界。

### 7.8 验收标准

1. 消费日志详情弹窗具备请求概览、消耗明细、计费详情和最终扣费四个层次。
2. 输入、输出、缓存读取和缓存命中率能与当前日志真实数据一致。
3. 计费详情能看懂每个 Token 项如何计算、倍率如何生效以及最终扣费如何得到。
4. 不同计费类型、模型映射、流式请求、错误请求、缓存为空和特殊扣费日志不会显示错误或无意义字段。
5. 详情弹窗关闭、再次打开其他日志、切换分页和筛选后页面状态正常。
6. 管理员与普通用户看到的详情字段符合权限要求，新增文案可正常切换语言。
7. 桌面端和移动端均无内容溢出、遮挡或无法关闭弹窗的问题。
