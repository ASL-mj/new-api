# 多密钥金额限额与二开功能国际化设计

## 1. 目标

本次修复同时解决两个问题：

1. 多密钥管理中的限额输入和用量展示必须与管理员选择的货币单位一致，不能把 NewAPI 内部原生额度直接当成金额展示。
2. 本分支相对官方基线新增的前端页面、操作提示、接口响应和系统事件需要补齐多语言支持。

本次只修改本地二开分支，不修改线上服务器，不改变现有渠道限额数据库单位，也不修改已经稳定运行的请求结算公式。

## 2. 根因结论

### 2.1 后端结算单位没有混用 Token

文本请求结算会同时生成两个独立数据：

- `summary.Quota`：已经应用模型倍率、补全倍率、分组倍率和 `QuotaPerUnit` 的 NewAPI 内部额度整数。
- `summary.TotalTokens`：上游返回的实际 Token 数。

`service.RecordRelayChannelUsage` 将两者分别传给渠道用量结算：

- `Quota` 累加到 `channels.quota_limit_used` 和 `channel_key_usages.quota_limit_used`。
- `TokenUsed` 只写入 `channel_usage_daily.token_used`，用于 Token 统计。

因此后端限额账本实际累计的是计费额度，不是原始 Token 数。

### 2.2 单位错位发生在多密钥前端

渠道编辑弹窗已经使用 `displayAmountToQuota` 和 `quotaToDisplayAmount` 在金额与原生额度之间转换；但多密钥管理弹窗存在以下问题：

- 编辑密钥限额时直接把 `quota_limit` 填入输入框。
- 提交时直接把输入值作为 `quota_limit` 发给后端。
- “已用/限额”直接展示 `quota_limit_used / quota_limit` 原始整数。

所以管理员看到和填写的是原生额度整数，却会把它理解为金额。该数字又与按 Token 计费产生的额度值同量级，因此表现为“系统按 Token 数计数”。

## 3. 方案比较

### 3.1 方案 A：只修改后端累计公式

将每次请求的 `TotalTokens` 或金额浮点值直接写入限额字段。

缺点：会破坏 NewAPI 现有额度体系，引入浮点误差，并导致渠道限额、用户额度和日志消耗使用不同单位。该方案不采用。

### 3.2 方案 B：修改接口改为传金额

让多密钥接口接收金额，再由后端按系统汇率转换为原生额度。

缺点：接口行为依赖前端显示币种和管理员个人设置，后端无法可靠知道该金额是美元、人民币还是自定义货币；也会破坏现有 API 契约。该方案不采用。

### 3.3 方案 C：保留原生额度作为唯一存储单位，在前端边界转换

数据库和接口继续使用原生额度整数；多密钥弹窗与渠道、令牌管理使用相同的金额转换函数和 UI 模式。

优点：不迁移数据、不改变结算逻辑、不产生浮点累计误差，并与 NewAPI 现有额度体系一致。本次采用该方案。

## 4. 多密钥限额修复设计

### 4.1 金额输入

编辑单个密钥限额时默认展示当前货币金额：

- USD：`$`
- CNY：`¥`
- CUSTOM：管理员配置的自定义货币符号
- TOKENS：继续展示原生额度数字

弹窗使用 `quotaToDisplayAmount(record.quota_limit)` 初始化金额输入；提交时使用 `displayAmountToQuota(amount)` 转回整数 `quota_limit`。

输入 `0` 仍表示无限额。金额输入允许 6 位小数，原生额度始终四舍五入为整数。

### 4.2 原生额度输入

沿用令牌和渠道编辑弹窗的交互，在金额输入下提供“使用原生额度输入”折叠项：

- 默认收起。
- 展开后可直接编辑整数额度。
- 金额输入和原生额度输入双向同步。
- 提交时只发送最终原生额度。

### 4.3 用量展示

多密钥列表的“已用/限额”使用 `renderQuota` 展示：

- 当前显示币种为金额时显示货币符号和金额。
- 当前显示模式为 TOKENS 时显示原生额度数字。
- 无限额继续显示 `∞`。
- 进度条仍使用原生整数计算比例，避免格式化字符串参与计算。

渠道编辑弹窗中的“当前限额已用”也改为 `renderQuota`，保证同一功能内单位一致。

### 4.4 API 与数据库

以下契约保持不变：

- `PUT /api/channel/:id/key-usages/:fingerprint/limit` 的 `quota_limit` 仍是整数原生额度。
- `channel_key_usages.quota_limit` 和 `quota_limit_used` 仍是 `BIGINT`。
- 已有数据不迁移、不重算。
- 后端继续用结算后的 `Quota` 累计限额，用 `TokenUsed` 记录 Token 统计。

## 5. 前端国际化设计

### 5.1 覆盖语言

前端完整覆盖现有七种语言：

- 简体中文 `zh-CN`
- 繁体中文 `zh-TW`
- 英文 `en`
- 法文 `fr`
- 日文 `ja`
- 俄文 `ru`
- 越南文 `vi`

### 5.2 覆盖模块

以官方基线 `bee339d2` 到当前分支的差异为范围，至少覆盖：

- 模型性能采集、模型卡片状态和性能抽屉。
- 渠道状态配置。
- 分组状态卡片、列表、详情和刷新提示。
- 运维监控、指标明细、排行、服务器状态和系统日志。
- 渠道限额、多密钥管理和渠道用量三列。
- 数据看板新增的用户 Token 排行和调用次数排行。
- 文档内嵌、首页与设置迁移新增提示。
- 新增导航项、按钮、空状态、错误提示和成功提示。

### 5.3 翻译键规则

继续遵循本版本 NewAPI 的前端约定，以简体中文原文作为 i18next key：

```jsx
t('密钥限额已更新')
t('{{seconds}} s 后刷新', { seconds })
```

禁止在新增 UI 中直接渲染中文字符串。工具函数不能返回已经拼接好的中文句子；应返回状态值或接受 `t` 后生成本地化文本。

动态选项如运维周期和监控状态虽然通过 `t(option.label)` 使用，也必须显式加入全部语言包，避免提取工具漏掉动态 key。

### 5.4 完整性校验

使用现有 `i18next-cli` 做全量提取和检查，并增加针对二开 key 的测试，至少保证：

- 七个语言包拥有相同的二开 key 集合。
- 任何语言都没有空翻译值。
- 插值变量名称在各语言中保持一致，例如 `{{count}}`、`{{seconds}}`。
- 二开页面不再直接渲染遗漏的中文文案。

## 6. 后端国际化设计

### 6.1 API 响应

后端继续覆盖现有三种语言：

- `zh-CN`
- `zh-TW`
- `en`

在 `i18n/keys.go` 增加渠道限额、监控分组、分组状态和运维接口的消息键，并在三个 YAML 语言包中提供翻译。

自定义控制器的可预期校验错误和操作成功响应使用：

- `common.ApiErrorI18n`
- `common.ApiSuccessI18n`

需要从模型层或服务层向上传递的业务错误使用带翻译键和模板参数的结构化错误；控制器响应时翻译。数据库错误和不可预期内部错误不伪装成业务错误。

### 6.2 系统运行日志

系统事件在写入时增加可选的结构化翻译信息：

- `message`：保留可读的默认原文，兼容旧客户端和数据库排查。
- `message_key`：稳定翻译键。
- `extra`：继续保存事件参数，也作为翻译模板参数来源。

查询系统事件时，如果记录包含 `message_key`，控制器根据当前管理员语言生成响应中的 `message`；没有 `message_key` 的历史记录直接返回原文。

该设计满足：

- 新日志可按查看者语言显示。
- 已有历史中文日志无需迁移。
- 数据库中的原始事件仍然可读。
- 前端不需要复制后端事件翻译规则。

## 7. 测试设计

### 7.1 金额限额回归测试

前端测试覆盖：

1. `$1` 在 `QuotaPerUnit=500000` 时提交 `500000`。
2. 已用 `250000`、限额 `500000` 时金额展示为 `$0.50 / $1.00`。
3. CNY 和自定义货币按现有汇率转换。
4. TOKENS 模式保持整数输入和展示。
5. `0` 在输入、接口和展示中始终表示无限额。

后端测试覆盖：

1. `Quota` 与 `TokenUsed` 分别写入额度和 Token 字段。
2. 密钥限额只按 `Quota` 增长，不能因 `TokenUsed` 较大而提前耗尽。
3. 达限后的自动禁用语义保持不变。

### 7.2 国际化测试

前端执行：

```bash
npm run i18n:lint
npm run build
```

后端执行目标模块测试和完整 Go 测试，验证三种语言的成功、校验失败和系统事件响应。

## 8. 验收标准

1. 多密钥限额默认以金额输入，最终仍以整数原生额度保存。
2. 多密钥“已用/限额”和渠道“当前限额已用”按当前货币设置展示。
3. 实际 Token 数不再被误解为密钥限额金额，后端额度与 Token 字段有回归测试隔离。
4. 全部二开前端功能在七种语言下没有回退到简体中文的新增文案。
5. 全部二开 API 的可预期消息支持简中、繁中和英文。
6. 新系统事件按查看者语言返回，旧事件继续显示原文。
7. 前端构建、i18n 检查和相关 Go 测试全部通过。
